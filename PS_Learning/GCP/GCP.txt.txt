# Cloud load balancing
	- Distribute user traffic across instances of an application in single region or multiple region.
	- Fully distributed, software defined managed service.
	- Features
		* High availability
		* Auto Scaling
		* Resiliency
	- Terminology
		* Backend : Group of endpoints that receive traffic from a GCP load balancer.
		* Frontend: Specify an IP address, port or protocol. This IP address is the frontend IP for the client requests.
		* Host and path rules: Define rules redirecting the traffic to different backends.
			^ Based on path : in28min/a, in28min/b
			^ Based on host : a.in28min, b.in28min
			^ HTTP headers (Auth Header) and methods
	- Proxy load balancing : It involves the load balancer acting as an intermediary for client requests. It receives requests from clients and proxies them to backend instances. The load balancer terminates the client's connection and establishes a new connection to the backend.
	- Pass through load balancing : It involves the load balancer simply passing newtwork packets to the backend instances without terminating them. It is typically used with TCP/UDP traffic.

# IAM
	- In GCP , roles are predefined set of permissions but in AWS, roles are set of permissions attached to entities which can assume that role.
	- AWS (Amazon Web Services) and GCP (Google Cloud Platform) both offer roles and policies as part of their Identity and Access Management (IAM) services, but there are some nuances in how these services operate within each platform. Here's a breakdown of the differences and similarities:

		### AWS:

		- **Roles:**
		  - In AWS, a role is an entity that defines a set of permissions for making AWS service requests.
		  - Roles can be assumed by trusted entities, which can be an IAM user, an AWS service, or an external user or application.
		  - Roles are often used to grant permissions to entities that do not have a fixed identity, such as applications running on EC2 instances.
		  - Roles include temporary security credentials that can be assumed by trusted entities.

		- **Policies:**
		  - Policies in AWS are JSON documents defining permissions. They can grant or restrict access to AWS resources.
		  - AWS policies are of several types, including managed policies (AWS-managed or customer-managed) and inline policies (embedded directly into a user, group, or role).
		  - Policies define what actions are allowed or denied and on which resources, using a fine-grained permission model.
		  - Policies are attached to IAM identities (users, groups, roles) to define their permissions.

		### GCP:

		- **Roles:**
		  - In GCP, roles are a collection of permissions. They consist of predefined roles, custom roles, and basic roles.
		  - Predefined roles provide granular access for specific GCP services and predefined use cases.
		  - Basic roles (Viewer, Editor, Owner) offer more general permissions across GCP services but are less granular.
		  - Custom roles allow users to combine specific permissions into roles tailored to their needs.
		  
		- **Policies:**
		  - Policies in GCP are known as IAM policies and consist of a set of bindings applied to resources.
		  - Each binding in a policy associates one or more members with a role.
		  - Policies define who (members) has what type of access (roles) to which resource (using resource hierarchies).
		  - IAM policies are applied at different resource levels (project, folder, organization), and they inherit down the resource hierarchy.
		  
		### Key Differences and Similarities:

		- **Granularity and Flexibility:**
		  - Both AWS and GCP offer granular permission models, but the implementation and terms may differ. AWS uses policies to assign permissions directly to identities or roles, while GCP uses roles within IAM policies that bind members to specific actions.
		  
		- **Resource Hierarchies:**
		  - GCP has a clear resource hierarchy which supports inheritance of policies, simplifying complex organizational structures. AWS doesn't have this direct inheritance mechanism; policies need to be explicitly set at each level.

		- **Role Definition:**
		  - AWS roles are dynamically assumed and include temporary security credentials. They are often used for cross-account access or to manage permissions for applications on services like EC2. GCP roles are static in that they are assigned to users or service accounts and do not involve temporary credentials by default.

		- **Terminology and Application:**
		  - While both platforms use similar concepts, terminology and specific implementations differ, which can influence how policies are structured and applied across resources.
	
	- Can we basically say, policy in GCP is somewhat similar to roles in AWS
		In a very broad sense, you could say that GCP's approach to IAM policies serves a similar purpose as AWS roles, in that both are ways of managing permissions and access to resources. However, it's important to understand their distinct functions and structures:

		### GCP Policies vs. AWS Roles:

		1. **GCP Policies:**
		   - **Function:** Define who (the members) has what level of access (via roles) to which resource.
		   - **Structure:** Consist of bindings that associate one or more members (users, groups, service accounts) with a role.
		   - **Hierarchy:** Policies are applied at different levels of the GCP resource hierarchy (such as organization, folder, project), and permissions can be inherited downstream.

		2. **AWS Roles:**
		   - **Function:** Define a set of permissions to make AWS service requests, which can be assumed by identities.
		   - **Structure:** Include policies (attached or inline) that specify allowed or denied actions on resources.
		   - **Access:** Often used for providing permissions to compute resources and establishing trust relationships for cross-account or external access.

		### How They Compare:

		- **Purpose:**
		  - Both are used for granting access and defining permissions, but GCP IAM policies are more about binding roles to members, while AWS roles are about temporarily assuming permissions for actions on AWS resources.

		- **Definitions:**
		  - In **GCP**, the IAM policy binds a role (a collection of permissions) to users or services. This separates the specification of permissions (roles) from the assignment (policies).
		  - In **AWS**, roles themselves carry permissions via attached policies, and they are temporarily taken on by entities (like services or users), often serving for dynamic use cases and cross-service access.

		- **Dynamic vs. Static:**
		  - **AWS roles** often exhibit dynamic behavior, especially in scenarios like EC2 with IAM roles, allowing temporary security credentials.
		  - **GCP roles** typically act as predefined sets of permissions or custom configurations permanently granted through policy bindings.

		### Summary:

		While there are conceptual overlaps between GCP policies and AWS roles in terms of managing and applying permissions, they are not directly equivalent due to differences in how each cloud provider structures and executes access control. Understanding these roles within their respective frameworks is critical for effective cloud resource management.

# Pub/Sub
	- Reliable, scalable, fully managed, asynchronous messaging service
	- Backbone of high available and high scalable solutions
	
	- Working
		* Publisher - Sender of a message
			^ publishers send messages by making HTTPS reqests to pubsub.googleapis.com
		
		* Subscriber - Receiver of the message
			^ Pull - Subscriber pulls message when ready [SQS]
			^ Push - Messages are sent to subscribers [SNS]
				` Subscribers provide a webhook endpoint at the time of registration
				` When a message is received on the topic, a HTTPS POST request is sent to the webhook endpoints.
		
		* Very flexible
			^ Publisher and subscriber relationship : One to many, Many to one and many to many
	
	- Topics and Subscriptions
		* Topic is created.
		* Subscriptions are created.
			^ Subscribers register to the topic.
			^ Each subscription represents discrete pull of messages from a topic.
			^ Multiple clients pull same subscription => messages split between clients.
			^ Multiple clients create a subscription each => each client will get every message.
	
	- Sending and Receiving messages
		* Publisher send a message to a topic.
		* Messages individually delivered to each and every subscription.
			^ Subscribers can receive messages either by :
				` Push : Pub/Sub sends the message to Subscriber
				` Pull : Subscribers poll for messages
		* Subscribers send ackowledgement(s).
		* Messages(s) are removed from subscriptions message queue
			^ Pub/Sub ensures messages is retained per subscription until it is acknowledged.
			
	- Differnce between SQS and SNS	
		* Amazon SQS
			^ Queue-based model: You create a queue, and producers send messages to it. Consumers poll the queue to retrieve messages.
			  Point-to-point communication: One message is typically consumed by one receiver.
			  No topic or subscription concept: It's simpler and more direct.
		* Google Cloud Pub/Sub
			^ Topic-based model: You create a topic, and producers publish messages to it.
			  Consumers must create subscriptions to receive messages from the topic.
			  Publish-subscribe pattern: One message can be delivered to multiple subscribers.
		
		More like Amazon SNS + SQS combo:
		SNS = Topic
		SQS = Subscription (if you connect SNS to SQS)

# Networking - Google Cloud VPC
	- Your own isolated network in GCP Cloud.
	- You control all the traffic coming in and going out of VPC.
	- Create all resources within VPC.
	- VPC is a global resource and contains subsets in one or more region.
	
	- VPC Creation and subnets
		* By default, each project has a default VPC.
		* Types of VPC:
			^ Auto mode :
				` Subnets are automatically created in each region.
				` Default VPC created automatically in the project uses auto mode.
			
			^ Custom mode :
				` No subnets are automatically created.
				` You have complete control over subnets and IP ranges.
				` Recommended for production.
	
	- CIDR block
		* A CIDR block consists of a starting IP address (69.208.0.0/28)
			^ It indicates that the first 28 bits out of 32 are fixed.
			^ 2^4 = 16
	
	- Firewall Rules
		* Configure firewall rules to control traffic going in or out of the network.
		* Stateful.
		* Each firewall rule has priority (0-65535) assigned to it.
		* 0 has highest priority. 65535 has least priority.
		* Default implied rule with lowest priority (65535).
			^ Allow all egress.
			^ Deny all ingress.
			^ Default rules can't be deleted.
			^ You can override default rules by defining by defining new rules with priority 0-65535.
		* Ingress Rule : Incoming traffic from outside to GCP targets.
		* Egress Rule  : Outgoing traffic to destination from GCP targets.
		* Along with each rule, we can also define
			^ Priority : Lower the number, higher the priority.
			^ Action on Match - Allow or Deny traffic.
			^ Protocol : ex TCP or UDP or ICMP
			^ Port : Which port
			^ Enforcement status : Enable or disable.
	
	- Shared VPC
		* When organisation has multiple projects and we want resources in different projects to talk to each other.
		* Created at organisation or shared folder level (Access Needed : Shared VPC Admin)
		* Allows VPC network to be shared between projects in same organisation.
		* Shared VPC contains one host project and multiple service projects
			^ Host project - Contains shared VPC Network
			^ Service project - attached to host projects.
		* It helps us achieve seperation of concerns.
			^ Network administrators responsible for Host projects and resource users use service projects.
	
	- VPC Peering : Connecting VPC networks across different organisations.
	- Cloud VPN : Connect on premise network to the GCP Network.
	- Cloud Interconnect : High speed physical connection between on-premise and VPC networks.
		* Direct Peering

Security Group in GCP - Firewall rules

suppose within a VPC, I am having 5 compute instances, but I want different kind of IP access for each instance, is it possible to achieve it, like we have the option of secuity group in AWS
	Yes, in Google Cloud Platform (GCP), you can achieve similar outcomes to what AWS Security Groups offer by using **Firewall Rules** in combination with **network tags** or **service accounts** to manage different kinds of IP access for each VM instance within a VPC. 

	Here's how you can achieve different IP access for each instance:

	1. **Network Tags**:
	   - Each VM in GCP can be assigned one or more network tags. Firewall rules can be configured to apply to VMs with specific tags, allowing you to define different access rules for different instances.
	   
	   - For example, if you have five instances and you want different rules for each:
		 - Assign a unique network tag to each instance (e.g., `instance1-tag`, `instance2-tag`, etc.).
		 - Create firewall rules that specify the tag in their target field, along with the desired IP ranges, protocols, and ports to allow or deny.

	2. **Service Accounts**:
	   - Firewall rules can also be applied based on the service account associated with the VM. By using different service accounts for your instances, you can control access based on these assignments.

	3. **IP-based Rules**:
	   - You can also directly define rules that apply to specific IP addresses, ranges, and subnetworks, although this is less flexible than using tags or service accounts if you're managing dynamic instances.

	4. **Priority and Policy**:
	   - Make sure to set appropriate priorities for your firewall rules. Lower numbers have higher priority, so they will be applied first. This allows for precise control, similar to a security group allowing or denying traffic.

	Here’s an example workflow:
	- Assume you have VMs `vm1`, `vm2`, ..., `vm5`.
	- Assign each their own tag: `vm1-tag`, `vm2-tag`, etc.
	- Create a firewall rule for `vm1` allowing SSH from a specific IP range with target as `vm1-tag`.
	- Create a different rule for `vm2` allowing HTTP access from another set of IPs with target as `vm2-tag`.
	- Continue similarly for the other VMs.

	By carefully designing and applying these rules, you can achieve highly customized network configurations for each of your compute instances in GCP, similar to the flexibility offered by AWS Security Groups.
	
	Certainly! Let's walk through an example where you have five VM instances within a Google Cloud VPC, and you want to apply different IP access rules to each instance.

	### Assumptions
	- **VM Instances**: `vm1`, `vm2`, `vm3`, `vm4`, `vm5`
	- **Network Tags**: `vm1-tag`, `vm2-tag`, `vm3-tag`, `vm4-tag`, `vm5-tag`

	### Desired Firewall Rules
	1. **VM1**: Allow SSH (port 22) only from `192.168.1.0/24`.
	2. **VM2**: Allow HTTP (port 80) traffic from `203.0.113.0/24`.
	3. **VM3**: Allow all outgoing traffic, but restrict incoming traffic.
	4. **VM4**: Allow RDP (port 3389) from `198.51.100.0/24`.
	5. **VM5**: Deny all external traffic, allow only internal subnet `10.0.0.0/16`.

	### Steps to Create Firewall Rules

	#### 1. Assign Network Tags to VMs
	- Ensure each VM has an appropriate tag:
	  - `vm1` is tagged with `vm1-tag`
	  - `vm2` is tagged with `vm2-tag`
	  - `vm3` is tagged with `vm3-tag`
	  - `vm4` is tagged with `vm4-tag`
	  - `vm5` is tagged with `vm5-tag`

	#### 2. Create Firewall Rules

	**For `vm1`: Allow SSH from `192.168.1.0/24`**
	```bash
	gcloud compute firewall-rules create allow-ssh-vm1 \
		--network=default \
		--priority=1000 \
		--direction=INGRESS \
		--action=ALLOW \
		--rules=tcp:22 \
		--source-ranges=192.168.1.0/24 \
		--target-tags=vm1-tag
	```

	**For `vm2`: Allow HTTP from `203.0.113.0/24`**
	```bash
	gcloud compute firewall-rules create allow-http-vm2 \
		--network=default \
		--priority=1000 \
		--direction=INGRESS \
		--action=ALLOW \
		--rules=tcp:80 \
		--source-ranges=203.0.113.0/24 \
		--target-tags=vm2-tag
	```

	**For `vm3`: Allow all outgoing traffic, restrict incoming**
	- GCP's default behavior allows all egress. You may only need to ensure that no ingress rules allow unwanted access. For demonstration:

	```bash
	# Restrict all ingress if no other rules are desired
	gcloud compute firewall-rules create deny-ingress-vm3 \
		--priority=1000 \
		--direction=INGRESS \
		--action=DENY \
		--rules=all \
		--target-tags=vm3-tag
	```

	**For `vm4`: Allow RDP from `198.51.100.0/24`**
	```bash
	gcloud compute firewall-rules create allow-rdp-vm4 \
		--network=default \
		--priority=1000 \
		--direction=INGRESS \
		--action=ALLOW \
		--rules=tcp:3389 \
		--source-ranges=198.51.100.0/24 \
		--target-tags=vm4-tag
	```

	**For `vm5`: Deny all external traffic, allow only internal subnet `10.0.0.0/16`**
	```bash
	# Allow intra-VPC traffic
	gcloud compute firewall-rules create allow-internal-vm5 \
		--network=default \
		--priority=1000 \
		--direction=INGRESS \
		--action=ALLOW \
		--rules=all \
		--source-ranges=10.0.0.0/16 \
		--target-tags=vm5-tag

	# Deny all other ingress
	gcloud compute firewall-rules create deny-external-vm5 \
		--priority=1100 \
		--direction=INGRESS \
		--action=DENY \
		--rules=all \
		--target-tags=vm5-tag
	```

	These firewall rules configurations allow you to manage access per VM instance, achieving flexibility similar to AWS Security Groups by using network tags to target specific instances for specific rules. Make sure each VM is correctly tagged and test the firewall rules to validate access control works as intended.
